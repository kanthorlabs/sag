## Checks without a finding

- Request paths [tested]: no request reached the MCP handler without a valid JWT. 7 HTTP methods on `/mcp` and 15 other paths (`/mcp/`, `/MCP`, `//mcp`, `/x/../mcp`, `/%6dcp`, `/healthz/../mcp`, `/healthz/`, `/%68ealthz`, `/healthz;x`, and others) give `401` without a JWT. Only `GET /healthz`, with or without a query, returns `200` without a JWT, with an empty body. `HEAD /healthz` and `POST /healthz` give `401`. A JWT in the query, in a cookie, or in `X-Authorization` gives `401`. `GET`, `DELETE`, `PUT`, `PATCH`, `OPTIONS`, and `HEAD` on `/mcp` with a JWT give `405`.
- Origin check [tested]: 17 header cases with a JWT (14 `Origin` forms and 3 other headers) and 9 `Origin` forms without a JWT. A listed value passes. A trailing `/`, upper case, a default port, a suffix host, `null`, an empty value, a comma pair in one value, and 2 `Origin` headers give `403` with no body and no `WWW-Authenticate`. Each `403` writes one record with `auth_cause: origin`. `GET /healthz` with an unlisted `Origin` gives `403`. The check runs before the JWT check (`internal/endpoint/server.go:68`).
- CSRF and DNS rebind [tested] [read]: SAG reads the JWT only from one `Authorization` header, so a browser holds no ambient credential. A request with `Content-Type: text/plain` or a form type gets `415` after the JWT check. An `OPTIONS` preflight gets `403` for an unlisted origin and `401` for a listed origin. No response has a CORS header. A rebind attack also needs a TLS certificate that the browser accepts for the attacker name.
- MCP methods and audit [tested]: 18 methods with no version header, with `2025-06-18`, and with `2026-07-28`, plus 4 notifications and 1 client response. None returned resource data, and none wrote a record. `initialize`, `ping`, `tools/list`, and `server/discover` return only protocol data. `resources/list`, `resources/templates/list`, and `prompts/list` return empty lists. `tools/list` is equal for 2 agents and holds no resource name. Each `tools/call` that reached dispatch wrote exactly 1 record, also for protocol `2026-07-28` and for an unknown tool.
- Unknown tool [tested]: the result is an `ErrorResult` with `invalid_argument`, the text `unknown tool`, and the `request_id` of the record. The tool name is not in the result. The record holds at most 63 bytes of the name.
- Authorization oracle [tested]: for `sql_query`, `sql_list_tables`, and `sql_describe_table`, the result bodies are equal (apart from `request_id`) for a foreign served resource, a foreign pending resource, a foreign unavailable resource, an absent name, an empty name, `R`, and a name of 5,000 bytes. The agent's own unavailable resource gives `resource_unavailable`. `list_resources` for each of 2 agents holds only its own served resources. Over 3 rounds of 1,500 calls, the 10th percentile latency is 61 to 64 µs for a foreign, an absent, and a foreign pending resource.
- Agent messages (R1, R5) [tested] [read]: each `core.Error` message is a constant, or a constant plus a field name, a hard maximum, or a SQLSTATE. 69 argument cases returned only fixed text. `errorResult` maps a code outside the 9 codes, an empty message, and a non-`core.Error` to `internal` (`internal/mcpserver/errors.go:27-41`).
- Result shape [tested]: a success result has one text item and `structuredContent` with the same JSON value. An error result has `isError: true` and no `structuredContent`. Claude Code 2.1.332 reads such an error result and reports its message.
- Cancellation on PostgreSQL 17 [tested]: with protocol `2026-07-28`, a client disconnect ended the PostgreSQL statement in less than 0.7 s, and the slot returned. With `2025-06-18`, the statement ran to its timeout of 8 s. After 60 start and disconnect cycles in 7.4 s with `pool_size: 5`, at most 1 backend was active, and the next query passed. Each cycle wrote 1 record.
- Server read timeout [tested]: a statement of 14 s with `timeout_seconds: 30` returned its result on HTTP/1.1 and on HTTP/2, for both protocol versions. `ReadTimeout: 10s` does not cancel a handler.
- Semaphore [tested]: a batch of 400 `sql_query` calls in one request gave 20 results and 380 `rate_limited` results with `max_concurrent_per_agent: 20`. A disconnect with protocol `2026-07-28` frees the slot at once.
- Claude Code protocol [tested]: Claude Code 2.1.332 sends `Mcp-Protocol-Version: 2026-07-28` over HTTP/1.1 and sends no `Origin` header. It calls `server/discover`, `tools/list`, `subscriptions/listen`, and `tools/call`. The PRD statement at `docs/PRD.md:557` is correct.
- Unit mutations [tested]: of 70 mutations in `endpoint`, `mcpserver`, `sql`, `pipeline`, `inventory`, `config`, and the runner, the unit tier fails for 64. 2 survivors are equivalent or accepted: the body limit before the Origin check, and text with other bytes but an equal JSON value. 1 survivor (the daemon does not pass `allowed_origins`) fails AC28. The last 3 are in S5.
- e2e mutations [tested]: on PostgreSQL 17, each of these 13 mutants fails its AC. AC28: no Origin check; the Origin check after the JWT check; no record for a `403`; an empty origin list in the endpoint. AC29: `resource_unavailable` for a foreign resource; no agent check; `list_resources` without a filter. AC30: `duration_ms` on a catalog tool; text other than `structuredContent`; no `openWorldHint`; no untrusted-data sentence; no `structuredContent`. AC31: `sql_query` returns `internal`.
- Runner secrets [tested]: the JWT is only in `mcp.json` (mode 0600) inside a `MkdirTemp` directory (mode 0700). The process arguments and the environment of `claude` do not hold it. `RunClaude` removes the directory on return and on a timeout. AC31 replaces the JWT in each failure message (`e2e/ac31_test.go:66-67`).
- Layer 1 to 4 controls [tested] [read]: the diff changes no file of `core`, `pipeline`, `token`, `audit`, `scrub`, `postexec`, `adapter`, `daemon`, `preflight`, `secret`, `keys`, `approval`, or `cli`. ## Findings

- S1 - status:FIXED - action:YES - Claude Code holds a `subscriptions/listen` stream that has no limit, no record, and that delays shutdown - [tested] `mcp.NewServer` gets no options (`internal/mcpserver/server.go:61`), so the SDK advertises `tools.listChanged: true`. Claude Code 2.1.332 then opens one `subscriptions/listen` request on `/mcp` and holds it for the full session. The SDK answers with an SSE stream that ends only when the client closes it. The stream takes no semaphore slot and writes no record. One JWT held 1,500 streams for 12 s with no refusal: about 112 KiB and 7 goroutines for each stream on HTTP/1.1, and 39 KiB on HTTP/2 (client and server together). With one open stream, `endpoint.Server.Run` returned 10.0 s after the stop signal with `context deadline exceeded` (`internal/endpoint/server.go:95-101`); without a stream it returned at once. [read] The daemon reports that error as fatal (`internal/daemon/run.go:153-155`), and the default Podman stop timeout is also 10 s. The SAG tool list never changes, so the capability is false. - fix:Pass `&mcp.ServerOptions{Capabilities: &mcp.ServerCapabilities{Tools: &mcp.ToolCapabilities{}}}` to `mcp.NewServer`. Add a unit test: `server/discover` shows no `listChanged`, and a `subscriptions/listen` request returns at once. Aelita verified this change in the copy: Claude Code opens no stream, `Run` stops at once, and AC26 and AC28 to AC31 pass on PostgreSQL 17. - why:Each SAG restart with a connected Claude Code session takes 10 s and ends as a failure, and PRD 11.3 needs a restart for each `agents` change. No limit stops one agent that holds streams until the daemon has no memory, and the audit log shows nothing. Aelita did not run that case to the end. The fix is one line.

- S2 - status:FIXED - action:YES - PRD 10.5 states that a batch writes no record, but a batch without a new version header runs each call - [tested] `docs/PRD.md:499` lists "a batch" as a request that the JSON-RPC layer rejects. This is true only with `Mcp-Protocol-Version` `2025-06-18` or later. With no header, or with `2024-11-05` or `2025-03-26`, the SDK accepts the batch. One request of 49 KB ran 400 `tools/call` entries and wrote 400 records. Each call passed the full pipeline and the semaphore, so no control is absent. `TestPreDispatchRejectionNotAudited` always sets `2025-06-18` (`internal/mcpserver/predispatch_test.go:29`, `:53`), so it does not show the other path. - fix:Change `docs/PRD.md:499`: a batch with protocol `2025-06-18` or later writes no record; an older batch runs each call and writes one record for each call. Add a test case without the header that asserts one record for each call of a batch. - why:The PRD text and the behavior must agree before the tag. The layer-4 review made the same statement from a probe that always sent `2025-06-18`. One request can write 400 records, which is relevant for the audit growth risk of PRD 7.6.

- S3 - status:FIXED - action:YES - More SDK errors repeat agent text than the accepted limit of PRD 10.2 names - [tested] `docs/PRD.md:460` accepts `-32602` only for `tools/call` `params` that do not decode. These responses also repeat request text: `prompts/get` (`unknown prompt "x"`), `resources/read` (`data.uri`), an unknown method (the method name, HTTP 400 or `-32601`), an `Mcp-Name` or `Mcp-Method` header that differs from the body (`-32020` with both values), and an unsupported version (`-32022` with `data.requested`). Each response comes from the SDK before dispatch, writes no record, returns no resource data, and holds only text of the same request. The scrubber does not run on it. - fix:Change `docs/PRD.md:460` to cover each MCP SDK protocol error before dispatch, with these 5 examples. Add them to `TestPreDispatchRejectionNotAudited` with an assertion of 0 records. - why:R1 and R5 permit fixed text only, and the accepted limit must name the full exception. The behavior has no oracle, so no code change is necessary.

- S4 - status:FIXED - action:YES - AC31 has no wait for the served state and depends on the Claude Code settings of the user - [read] `runAC31` starts Claude Code at once (`e2e/ac31_test.go:49-64`). Preflight runs after the daemon starts to serve (`internal/daemon/run.go:120-123`), and AC29 and AC30 wait up to 70 s for the served state. If `ac31` is not served, `sql_query` returns `resource_unavailable` and the marker is absent. [tested] The run loads the user settings: the answer of one run addressed Ulrich by name, and Claude Code called `sql_list_tables`, which is not in `AllowedTools`. The random marker still proves that a pass comes from a SAG read. - fix:Before `RunClaude`, wait until `list_resources` for `ac31` holds `ac31`, as `ac29Listed` does. After the run, assert one `allow` record with operation `query` for `sub` `ac31`. Optional: add `--setting-sources` to isolate the run. - why:AC31 passed in each of the 3 gate runs and in 2 review runs, so this is a risk of a false failure, not of a false pass. CI skips AC31. Do it with the layer-6 CI work.

- S5 - status:FIXED - action:YES - The runner can wait past its timeout, and no test fails for 3 runner mutations - [tested] `RunClaude` sets no `cmd.WaitDelay` (`e2e/harness/claude.go:71-85`). With a fake `claude` that starts `sleep 20`, a 2 s deadline returned after 20.0 s, because the child holds the output pipe. If `go test -timeout` then ends the process, the deferred `RemoveAll` does not run, and `mcp.json` with the JWT stays. No unit test fails when the runner puts the JWT in the arguments, drops `--strict-mcp-config`, or drops `--tools ""`. Each run also leaves one empty directory in the Claude Code `projects` directory; 4 from the gate runs are there. - fix:Set `cmd.WaitDelay = 5 * time.Second`. Make the fake `claude` print its arguments and environment, and assert that they hold no JWT and that both flags are present. - why:The JWT belongs to a test container that the suite removes, so the exposure is small. The changes are about 10 lines of test code and can wait.

- S6 - status:FIXED - action:YES - `sag config check` accepts `allowed_origins` entries that no browser sends - [tested] `validOrigin` (`internal/config/config.go:236-251`) accepts `https://*.example`, `https://münchen.example`, `https://127.1`, `https://[0:0:0:0:0:0:0:1]`, `https://agent.example.`, and a host with U+200B or U+00A0. The Origin check compares bytes, so each such entry never matches and the request gets `403`. The unit test rejects only the bare `*` (`internal/config/config_test.go:429`). - fix:Accept only a host of `[a-z0-9.-]` labels without a trailing dot, or an IP literal that is equal to its `netip.Addr` text. Add the 6 entries to `TestAllowedOriginsRejected`. Point the `server.allowed_origins` row of PRD 13.4 (`docs/PRD.md:636`) to section 11.4. - why:Each case fails closed, so no access opens. Decision F1 wants a wrong entry to fail at config check; an operator who writes a wildcard gets a silent `403`.

- S7 - status:FIXED - action:YES - A browser at a listed origin cannot call SAG - [tested] An `OPTIONS` preflight from a listed origin has no JWT and gets `401`. No SAG response has an `Access-Control-Allow-Origin` header. A browser needs a preflight for the `Authorization` header, so it stops before the `POST`. `server.allowed_origins` thus helps only a non-browser client that sends `Origin`. - fix:Change no code. Add to PRD 11.4: SAG sends no CORS headers, and a browser client is outside v1. - why:The v1 client is Claude Code, which sends no `Origin`. The state is safe; the PRD does not say that the key has no browser use.

- S8 - status:OPEN - action:NO - The input schemas and the pipeline differ for 4 groups of edge values - [tested] The pipeline accepts `"schema": null` on `sql_list_tables` and `sql_describe_table` as an absent key, and `list_resources` accepts `arguments: null`; the schemas reject both. The pipeline rejects `max_rows: 1.0` and `1e2`, which a JSON Schema `integer` accepts. The pipeline rejects a `schema` or `table` of 63 characters above 63 bytes, which `maxLength: 63` accepts (G2 records this one). 8 of 69 cases differ; the other 61 agree. - fix:Change no code. Optional: reject a JSON `null` for `schema` in `operationText`. - why:No case passes a harmful value: `null` equals the default, and each rejected value gets a fixed `invalid_argument` text. The SDK does not enforce the schema; the pipeline is the control.

- S9 - status:OPEN - action:NO - The audit record does not show a client disconnect - [tested] With protocol `2026-07-28`, a disconnect gives a record with `deny` and reason `timeout` after about 1 s, equal to a statement timeout (`internal/adapter/postgres/conn.go:254`). With an older protocol, the statement ends and the record is `allow` with its row count, but no client received the result. - fix:Change no code in layer 5. Optional later: map `context.Canceled` to its own audit reason, for example `timeout:client_cancel`. - why:The record stays on the safe side: it never hides a read. A new reason needs a decision on the closed reason set of PRD 10.5.

- S10 - status:FIXED - action:NO - The default e2e image tags on the machine hold layer-3 code - [tested] `localhost/sag:e2e` prints `sag sag-layer-3-5-g116b0a0`, and `localhost/sag-conformance:e2e` prints `sag sag-layer-3-8-gee35438`. Their creation times are 12:23 UTC and 12:20 UTC. Layer-4 finding S12 asked to rebuild or remove them and has `status:FIXED`. The AC report itself names version `sag-layer-4-7-g53957f1`, so the gate used a current image. - fix:Run `make image image-conformance` at `53957f1`, or remove the 2 tags. - why:This is machine state, not repository state, and `make e2e` builds the image first. A direct `go test -tags e2e` run tests old code, but AC28 then fails loudly.
