## Findings

- B1 - status:FIXED - action:YES - Field selection calls any function with one argument, and no function rule sees it - [tested] PostgreSQL resolves `(expr).name` and `alias.name` as the call `name(expr)` when no column has that name. The parse tree holds `A_Indirection` or `ColumnRef`, not `FuncCall`. `checkFunctionNames` reads only `FuncCall` (`internal/adapter/postgres/funcrules.go:66-67`). The allowlist permits both nodes (`allowlist.go:28`, `:59`). With empty name lists, `validateCatalog` sends no query (`catalog.go:52-54`). Through the product executor on PostgreSQL 17, each of these statements returned rows: `SELECT (SELECT 913001).pg_advisory_lock` (the lock stayed on the pooled session after `ROLLBACK`), `SELECT ('ssl_key_file'::text).current_setting`, `SELECT ('PG_VERSION'::text).pg_read_file`, `SELECT (1::float8).pg_sleep` (1.01 s), `SELECT ('SELECT to_tsvector(...) FROM pg_authid'::text).ts_stat` (the parts of the SCRAM hashes of 3 roles), `SELECT (7::int).p3_one` (a volatile PL/pgSQL function in `public` that takes an advisory lock), and `SELECT t.p3_full FROM p3_t t` (a function in `public`). The controls `SELECT pg_catalog.pg_advisory_lock(1)` and `SELECT current_setting('primary_conninfo')` rejected. The `psql` replay on 14.25, 17.12, and 19.0 gave the same results, and `('rev3_point'::text).pg_create_restore_point` returned a WAL position in the read-only transaction. A bare number, as in `(1).pg_sleep`, rejects with `render:lexer`; this is an accident of the deparser, not a rule. - fix:In `checkFunctionNames`, collect each `String` of `A_Indirection.indirection` and each `String` after the first of `ColumnRef.fields` into a new list of `pgTree`. In `validateCatalog`, look up these names in `pg_proc`. Reject a name when one match fails rule 1, 4, 5, or 6 of PRD 8.4. Let a name without a match pass, because it is a column. Add unit rows, integration rows, and AC15 e2e rows (advisory lock, `current_setting`, `pg_read_file`, `ts_stat`, a function in `public`) with the effect checks. Add the rule to PRD 8.4. - why:The bypass defeats rules 1, 3, 4, 5, and 6 for each function with one argument. It gives the effects of PRD 8.5 that C2 and C3 do not block, runs code outside `pg_catalog`, and reads credentials (PRD 8.6).

- B2 - status:FIXED - action:YES - One `sql_query` request below 16 KiB stops the daemon - [tested] The text `SELECT ARRAY`, 4,700 times `[`, `1`, 4,700 times `]` (9,413 bytes) ends the process with `SIGSEGV` inside `pg_query.Deparse` (`internal/adapter/postgres/parse.go:26`, called from `render.go:38`). Aelita ran the product dialect through `sql.NewExecutor(...).Execute` in `gcr.io/distroless/base-debian12:nonroot` with `--read-only --cap-drop=all --security-opt=no-new-privileges --user 65532:65532`. The stack limit was the default of 8,192 KiB. 4,000 levels pass. In `golang:1.27.4-bookworm`, 4,900 levels of `a(`, of `::a`, and of `[` end the process, and 4,500 levels pass. With a stack limit of 4,096 KiB, 5 of 14 shapes at 16,384 bytes end the process. `Parse` accepts about 4,995 node levels. The only bound is the recursion limit of the Go protobuf decoder (`proto: exceeded maximum recursion depth`). The C deparse path has no stack check, and `eachMessage` has no depth limit (`tree.go:28-48`). A `recover` in the handler does not catch a signal in C code. - fix:Reject a tree above a fixed depth in the static phase, before `Render`. Example: 500 node levels, which is about 1 MiB of C stack at 2 KiB for each level. Count the depth in `eachMessage` and return a `Rejection`. Add a unit test for each deep shape at 16,384 bytes and one test in the runtime image. Then assert the exact result at 16,384 bytes in `Product_SQLSizeLimit` (`e2e/product_test.go:168-170`). - why:An agent with a valid JWT stops the service for all agents with one request, and repeats it after each restart. This is finding B1 of layer 2 at the render stage. The 16 KiB limit does not cover it.
